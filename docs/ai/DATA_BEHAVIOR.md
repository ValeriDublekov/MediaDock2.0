# Persistence Behavior

Cross-component transaction boundaries, retry/recovery, data preservation, and provider side effects. For canonical ownership and migration cautions see [Data contracts](DATA_CONTRACTS.md); for entities and constraints see [Data schema](DATA_SCHEMA.md). HTTP behavior belongs to [API contracts](API_CONTRACTS.md) and [identity and personal data](API_IDENTITY_AND_PERSONAL_DATA.md). Linked services and repositories are authoritative for algorithms and persisted fields.

## RSS Ingestion

Each normalized torrent URL maps to one `torrent_releases` row globally. Rutracker topic URLs normalize to their topic ID; a known URL refreshes that row before title parsing or metadata lookup, including when observed through another RSS profile. The row retains the latest feed/profile details and points to its existing `torrent_movies` identity. The deduplication migration keeps the row with the greatest `LastSeenAt` (then greatest ID), removes item state for discarded rows, and deletes catalog rows left without releases. Parse logs and configured sources are retained. A scan is not one transaction: run creation, parse-log writes, item upserts, and the final summary are separate operations. A failed scan can therefore leave earlier item changes committed. See [`PostgresRssIngestionRepository`](../../server/src/MediaDock.Infrastructure/Ingestion/PostgresRssIngestionRepository.cs) and [`RssIngestionService`](../../server/src/MediaDock.Application/Ingestion/RssIngestionService.cs).

## Imports And Ownership

Personal-rating import validates the complete input before opening its transaction. New imported rows keep `is_manually_added = false`, and updates preserve the existing marker. Owner scoping and merge-without-deletion semantics are documented in the [personal ratings API contract](API_IDENTITY_AND_PERSONAL_DATA.md); persistence is implemented by [`PersonalRatingsApiService`](../../server/src/MediaDock.Api/PersonalRatings/PersonalRatingsApiService.cs).

Oscar import upserts `oscar_movies` and nominations transactionally, preserving source identity and enrichment state without requiring a `torrent_movies` row or IMDb match; it does not call OMDb. Golden Globes import writes award names, `golden_globe_titles`, and nominations transactionally. Reimports reuse the `(title, year, nominee_type)` identity, so a new nomination inherits the group's existing link and enrichment state. Type corrections move only the affected nomination unless a verified automatic link preserves the existing type. Provider metadata is read from `imdb_titles`, never copied into these source-owned records. See [`OscarDatasetImporter`](../../server/src/MediaDock.Infrastructure/OscarAwards/OscarDatasetImporter.cs) and [`GoldenGlobeDatasetImporter`](../../server/src/MediaDock.Infrastructure/GoldenGlobes/GoldenGlobeDatasetImporter.cs).

Favorites are keyed by `(user_id, imdb_id)`, so source screens share one per-user marker set for the same IMDb identity. Add requires an existing `imdb_titles` movie with `metadata_status = 'enriched'`; pending, failed, missing, or non-movie metadata is not eligible. `ToDownload` can be set before any RSS release exists. See [`FavoriteApiService`](../../server/src/MediaDock.Api/Favorites/FavoriteApiService.cs).

The recommendation watched action requires a `1..10` rating, rechecks that the movie is still eligible for the active user, then writes an owner-scoped `personal_ratings` row with `is_manually_added = true`. That rating removes the movie from that user's recommendations; the personal-ratings response exposes the marker for future filtering. See [`MovieRecommendationsApiService`](../../server/src/MediaDock.Api/Recommendations/MovieRecommendationsApiService.cs) and [`MovieRecommendationsEndpoints`](../../server/src/MediaDock.Api/Recommendations/MovieRecommendationsEndpoints.cs).

## Enrichment And Retry Persistence

Oscar enrichment saves each completed result before continuing. Its run record checkpoints progress, so abrupt termination can leave a `running` record at its last committed checkpoint. See [`OscarEnrichmentService`](../../server/src/MediaDock.Application/OscarAwards/OscarEnrichmentService.cs) and [`PostgresOscarEnrichmentRunRepository`](../../server/src/MediaDock.Infrastructure/OscarAwards/PostgresOscarEnrichmentRunRepository.cs).

Manual Golden Globes linking and refresh enqueue are transactional; the group owns the link version and enrichment state. Version-checked worker updates prevent an older in-flight result from overwriting a newer manual link or clear. See [`GoldenGlobeEnrichmentService`](../../server/src/MediaDock.Application/GoldenGlobes/GoldenGlobeEnrichmentService.cs) and [`PostgresGoldenGlobeEnrichmentRepository`](../../server/src/MediaDock.Infrastructure/GoldenGlobes/PostgresGoldenGlobeEnrichmentRepository.cs).

RSS, Oscar, Golden Globes, and personal IMDb enrichment share a persisted PostgreSQL OMDb request budget by UTC day. Each HTTP attempt, including a fallback or retry, reserves atomically; cache hits do not reserve, and a reservation remains charged if the process exits before sending the request. Provider quota exhaustion blocks further reservations for that UTC day across API restarts; batch work is deferred, while local budget denial leaves unprocessed candidates eligible. See [`PostgresOmdbRequestBudget`](../../server/src/MediaDock.Infrastructure/Metadata/PostgresOmdbRequestBudget.cs) and [`ImdbTitleEnrichmentService`](../../server/src/MediaDock.Application/PersonalRatings/ImdbTitleEnrichmentService.cs).

## Cache And Coordination

The dispatcher holds a PostgreSQL session advisory lock while it runs a claimed RSS scan, Oscar/Golden Globes enrichment job, or dataset import. A competing dispatcher leaves queued work for a later poll; this lock does not serialize ordinary API writes. See [`PostgresAdvisoryScanLock`](../../server/src/MediaDock.Infrastructure/Ingestion/PostgresAdvisoryScanLock.cs) and [`BackgroundJobDispatcher`](../../server/src/MediaDock.Api/BackgroundJobs/BackgroundJobDispatcher.cs).

## Recommendation Vote Freshness

`imdb_titles.normalized_vote_weight` is shared per canonical movie, not per user. The `general_recommendation_settings` singleton stores the median period, the dirty flag, and last-success metadata. User-selected score coefficients are request state and never enter these tables.

The PostgreSQL invalidation triggers mark weights dirty when a movie is inserted or a movie's year, IMDb vote count, or media type changes; changing the median period also marks the singleton dirty. The persistence migration marks it dirty when existing movie rows need their first calculation. See [`AddRecommendationVoteInvalidationTriggers`](../../server/src/MediaDock.Infrastructure/Persistence/Migrations/20261022140000_AddRecommendationVoteInvalidationTriggers.cs).

`POST /api/settings/recommendations/recalculate-votes` sets the dirty flag before opening its transaction, locks `imdb_titles` against concurrent input writes, recalculates and bulk-updates movie weights, then writes last-success metadata and clears the flag in the same transaction. The synchronous operation is limited to 10 seconds. A timeout rolls back the weight/metadata transaction and returns 504 while leaving the dirty flag set; a metadata write waiting on the table lock can then mark it dirty again. The web settings view keeps the warning visible until a fresh settings read reports clean. If the endpoint later uses `202 Accepted`, the web view polls that settings state until the flag clears. See [`RecommendationSettingsApiService`](../../server/src/MediaDock.Api/Recommendations/RecommendationSettingsApiService.cs) and [`MovieVoteNormalizer`](../../server/src/MediaDock.Application/Recommendations/MovieVoteNormalizer.cs).
