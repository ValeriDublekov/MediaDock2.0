## RSS Ingestion

[`SourceItemIdentity.From`](../../server/src/MediaDock.Application/Ingestion/RssIngestionContracts.cs) builds an occurrence key as `entry:<trimmed feed entry id>` when an entry ID is present; otherwise it uses `url:<trimmed torrent URL>`. It throws if neither value is present. PostgreSQL enforces uniqueness of `(source_id, source_item_key)`.

RSS item processing uses `rss_item_states`, keyed by source and item identity, separately from `metadata_cache`. Its SHA-256 fingerprint covers the raw title, torrent URL, publication timestamp, feed mode, parser version, and matching exclusions. New resolved items skip metadata lookup indefinitely while refreshing occurrence/title `LastSeenAt`; terminal decisions expire after two days. At rollout, unchanged prior occurrences and recent terminal logs are adopted for two days, then retried under the current parser. A changed fingerprint is reprocessed. `scan_runs.known_entries_skipped` distinguishes these skips from entries ignored by matching; `entries_seen` remains all feed entries read, and `omdb_requests` counts actual HTTP attempts.

[`PostgresRssIngestionRepository`](../../server/src/MediaDock.Infrastructure/Ingestion/PostgresRssIngestionRepository.cs) looks up a title by normalized IMDb ID first, then by normalized title, year, and media type only when the IDs are compatible. On the first real RSS observation it sets both title seen dates; later observations preserve the first and update the last. A title created by Oscar import is reused when its IMDb ID matches, without creating a duplicate title. A retry is limited to a violation of `ux_titles_imdb_id`, after clearing the EF tracker and rereading the canonical title; unrelated unique errors are not masked.

`UpsertCatalogItemAsync` commits the title/occurrence upsert in one transaction and rolls back on failure. A full scan is not one transaction: run creation, parse-log saves, each item upsert, and final run-summary save are separate repository operations.

## Imports And Ownership

The personal-ratings import validates the complete input before opening a database transaction, then normalizes IDs and merges by `(user_id, imdb_id)`: new IDs are inserted, changed ratings are updated, and identical ratings are left untouched. IDs absent from later files are never deleted. The file is processed in memory and is not persisted. See the [API contract](API_IDENTITY_AND_PERSONAL_DATA.md) for format, limits, and response behavior.

[`OscarDatasetImporter`](../../server/src/MediaDock.Infrastructure/OscarAwards/OscarDatasetImporter.cs) accepts compact CSV exports or the original tab-separated dataset and filters to `Year > yearAfter` plus exactly `BEST PICTURE`, `DIRECTING`, `WRITING (Original Screenplay)`, `WRITING (Adapted Screenplay)`, and `CINEMATOGRAPHY`. It normalizes IMDb IDs, matches `titles` by IMDb ID first, then uses normalized title/year only when IDs do not conflict; otherwise it creates a distinct title placeholder. Oscar-only placeholders have null `FirstSeenAt`/`LastSeenAt`. Re-import preserves populated title metadata and enrichment status, and upserts film and nomination rows in one transaction without creating occurrences or contacting OMDb. Nomination identity includes ceremony, category, film, nominee IDs (or name fallback), nominees, and `Detail`.

[`GoldenGlobeDatasetImporter`](../../server/src/MediaDock.Infrastructure/GoldenGlobes/GoldenGlobeDatasetImporter.cs) accepts CSV or TSV bytes with `nominee_type`, `year`, `winner`, `award`, and `title` columns. It keeps `film`, `movie`, `series`, and `tv-show` rows newer than `YearAfter`, skips unsupported types and blank titles, and imports nominations and award names transactionally. Its stable SHA-256 key makes repeat imports idempotent and preserves enrichment fields unless nominee type changes; a type correction clears stale enrichment state. Golden Globes import does not create canonical `titles` or torrent `occurrences` and does not call OMDb.

The `SystemSourceProfiles` migration preserves each RSS URL, replaces stored source names with fixed profile labels, activates configured URL rows, and maps legacy `series` values in sources, occurrences, or parse logs to `series_ongoing`. Removing a URL through the API disables its `sources` row rather than deleting it because occurrences, parse logs, and RSS item states retain its ID.

## Enrichment And Retry Persistence

[`OscarEnrichmentService`](../../server/src/MediaDock.Application/OscarAwards/OscarEnrichmentService.cs) selects the newest eligible candidates through `IOscarEnrichmentRepository`, resolves each with the shared metadata resolver, and saves each completed result before proceeding. It compares the OMDb IMDb ID with both `OscarFilm.ImdbId` and the linked `Title.ImdbId`; a conflict is a retryable `imdb_id_mismatch` and does not apply metadata. [`PostgresOscarEnrichmentRepository`](../../server/src/MediaDock.Infrastructure/OscarAwards/PostgresOscarEnrichmentRepository.cs) persists status, attempt timestamps/count, deferred retry time, and OMDb fields on the related `Title` in the same `SaveChanges` transaction. Provider quota exhaustion defers the current film until the next UTC day and stops the batch; a locally denied reservation leaves the unprocessed candidate eligible. Other temporary errors use capped exponential retry delay. Oscar metadata updates do not modify title observation dates or create occurrences.

[`GoldenGlobeEnrichmentService`](../../server/src/MediaDock.Application/GoldenGlobes/GoldenGlobeEnrichmentService.cs) groups candidates by title, ceremony year, and nominee type, then resolves through the shared metadata resolver. Search candidates are checked for title similarity, identity/type/year, and an OMDb `Awards` value containing `Golden Globe`; ambiguous or unverified results become `problem`, confirmed misses become `not_found`, and transient failures use capped exponential retry. Provider quota exhaustion saves/defer the current candidate and stops the batch; local budget denial leaves it eligible. [`PostgresGoldenGlobeEnrichmentRepository`](../../server/src/MediaDock.Infrastructure/GoldenGlobes/PostgresGoldenGlobeEnrichmentRepository.cs) applies each outcome only to nominations for that title, year, and type. Its requests increment shared `TotalRequests`, not the Oscar-only `OscarRequests`; it does not update canonical title metadata or create an enrichment-run audit row. The catalog can read poster URLs from unexpired found entries in the shared metadata cache.

Golden Globes batch enrichment selects non-manual `pending`, `problem`, and `not_found` nominations, due `temporary_error` nominations, and `enriched` nominations with invalid/missing IMDb IDs. Each title/year/type group is attempted once per run using the maximum attempt count among eligible nominations. `problem` and `not_found` are retried on the next manually started job; valid enriched rows and manual pins remain excluded.

Manual linking updates every nomination in the exact `(ceremony year, title, nominee type)` group and enqueues a `golden_globe_manual_refresh` job in the same transaction. Same-group/same-ID requests reuse an active job. Each set or clear increments the link version; the worker applies an outcome only when requested ID, manual pin, and version still match, preventing stale writes even after an A-to-B-to-A change. Batch enrichment excludes pinned nominations, and its conditional update cannot write through a manual pin. Manual lookups use the exact IMDb ID and persist it as `metadata_cache.lookup_identity`; clearing removes the pin, invalidates in-flight versions, and returns the group to `pending`. Re-import preserves pins unless nominee type changes; type correction clears the ID/pin and increments the version.

[`PostgresOscarEnrichmentRunRepository`](../../server/src/MediaDock.Infrastructure/OscarAwards/PostgresOscarEnrichmentRunRepository.cs) inserts a `running` record before candidate selection, checkpoints counts and actual resolver HTTP attempts during processing, then records final status and completion time. `quota_stopped` distinguishes local/provider cap stops; `error_code` stores an exception type or safe provider code, not exception text or request URLs. Abrupt termination can leave a `running` row with its last committed checkpoint.

[`PostgresOmdbRequestBudget`](../../server/src/MediaDock.Infrastructure/Metadata/PostgresOmdbRequestBudget.cs) uses one atomic PostgreSQL upsert per HTTP attempt. `omdb_daily_usage` stores total and Oscar request reservations by UTC date; RSS and Golden Globes usage are derivable as total minus Oscar. `DailyRequestLimitReached` records when the shared cap was met. A provider 429 or OMDb quota response records a safe error code and sets `ProviderQuotaExceeded`, preventing subsequent HTTP reservations for that UTC date across API restarts. Other failures update `LastErrorCode` with a bounded code, never provider text or request URLs. Each fallback and retry reserves separately; metadata-cache hits do not reserve. A reservation is intentionally conservative if the process exits after reservation but before sending the HTTP request. The API exposes the last 30 UTC days of aggregates to the provider settings screen.

`ImdbTitleEnrichmentService` resolves eligible IDs with OMDb's exact IMDb-ID lookup, verifies that returned IDs match, and writes successful metadata to `imdb_titles`. Its candidate query joins only ratings owned by the job owner and processes at most 100 IDs per job; pending rows and due temporary-error/not-found rows are eligible. Confirmed misses and transient errors retain metadata status and retry timestamps; quota exhaustion defers the current row until the next UTC day and stops the batch. Every HTTP attempt uses the same PostgreSQL request budget as RSS and award enrichment. The owner-scoped job is deduplicated while active; its status and events do not include rating IDs or scores. The personal-ratings list GET itself does no provider work.

## Cache And Coordination

The metadata cache key is a lowercase SHA-256 digest of versioned normalized title, year, source type, and year semantics. The resolver caches confirmed `found` results for 30 days and `confirmed_not_found` results for 2 days, not transient failures. Title-based lookup reuses unexpired positive and negative entries by normalized title and source type, including year-specific entries written by Oscar enrichment. Cache writes use a read-then-write by key followed by `SaveChanges`; PostgreSQL enforces the unique key, but the code does not provide a separate concurrent-upsert retry policy.

The API dispatcher acquires a PostgreSQL session advisory lock with `pg_try_advisory_lock` and releases it with `pg_advisory_unlock` for the duration of a claimed RSS scan, Oscar/Golden Globes enrichment job, or dataset import. A competing dispatcher leaves queued work untouched for a later poll. This is not a general lock for API writes. The implementation is [`PostgresAdvisoryScanLock`](../../server/src/MediaDock.Infrastructure/Ingestion/PostgresAdvisoryScanLock.cs); [`BackgroundJobDispatcher`](../../server/src/MediaDock.Api/BackgroundJobs/BackgroundJobDispatcher.cs) holds the lease across claim and handler completion.

For persistence verification, use the focused test categories in [Testing](TESTING.md). PostgreSQL integration tests apply migrations to disposable databases; they are not evidence of deployed production state.
