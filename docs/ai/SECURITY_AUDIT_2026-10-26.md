# Internet Exposure Security Audit (Reassessed 2026-10-30)

## Decision

**Do not expose the application origin directly to the internet or remove the existing Cloudflare Access gate yet.** API authorization still defaults off in Compose, so anonymous clients can access protected API groups unless the deployment explicitly enables enforcement. The current worktree now gates the React application on an active linked account and shows a welcome/sign-in view to anonymous visitors, but those frontend changes are uncommitted and do not enforce API access. The production server still serves the SPA bundle anonymously. The recommended target remains HTTPS-only Google sign-in followed by an active, administrator-approved MediaDock account. Keep Cloudflare Access as an additional perimeter gate if desired, but **do not treat Cloudflare Access or a React login screen as authorization for the API**.

The initial review was performed on 2026-10-26 and reassessed against the repository on 2026-10-30. This is a source/configuration review and focused automated-test review, **not** a penetration test or attestation of the running host. No production configuration, firewall, Cloudflare policy, deployed SHA, secrets, DNS, or external network path was inspected. The [production runbook](../../deploy/systemd/README.md) records a Cloudflare Access challenge on one date, but also records unverified direct-origin and router exposure; that historical observation is not evidence of today's policy. Repository source and tests are authoritative for intended behavior, not proof of what is deployed. The current worktree contains uncommitted UI and documentation changes; they are not assumed to be deployed.

## Findings

Severity refers to internet exposure of the reviewed code, not a claim about the presently deployed host.

| ID | Priority | Finding | Before exposure |
| --- | --- | --- | --- |
| A1 | **Blocker** | API authorization defaults off; anonymous callers can operate system and user-admin endpoints. | Enforce authorization in the deployment and fail closed on unsafe settings. |
| A2 | **Medium** | Current uncommitted UI gates app routes behind an active account, but static assets remain publicly served. | Verify, commit, and deploy the UI gate; protect API data independently. Gate assets only if their confidentiality is an explicit requirement. |
| A3 | **Blocker** | An HTTPS edge challenge alone does not close the direct HTTP/LAN/API origin. | Verify Cloudflare policy and every bypass path from outside the LAN; keep the origin private. |
| A4 | **High** | Unhandled API errors return raw exception messages. | Return a generic 500 and retain detailed errors only in protected logs. |
| A5 | **High** | Cookie-authenticated mutations do not have a uniform anti-forgery policy. | Inventory all mutations; validate tokens and origin as appropriate, including uploads and admin/deployment actions. |
| A6 | **High** | Login, registration, token issuance, and expensive operations have no application rate-limit policy. | Add per-route limits plus edge abuse controls, with trusted proxy/IP handling. |
| A7 | **Medium** | No explicit response security-header or private-response cache policy is configured in the reviewed app. | Set and verify headers at the HTTPS edge/app; test browser compatibility. |
| A8 | **Medium** | Cookie-protection key persistence, host secret posture, and image provenance are not established by this review. | Verify the host, persist/protect keys, review credentials and backups, pin/update images. |
| A9 | **Conditional High** | The restored-data Development mock can mistake a remote caller proxied through Vite for a loopback caller. | Keep the Vite dev server loopback-only and never tunnel, port-forward, or LAN-bind this restored-data workflow. |

### A1. Authorization is optional (blocker)

[Compose](../../compose.yaml) sets `GOOGLE_AUTH_ENABLED=false` and `ACCESS_CONTROL_ENFORCED=false` by default. In the [authorization handler](../../server/src/MediaDock.Api/Authentication/AccessControl.cs), unenforced policies succeed without resolving an active user except for explicitly owner-scoped personal routes. The [authentication tests](../../server/tests/MediaDock.IntegrationTests/GoogleAuthenticationApiTests.cs) confirm an anonymous client in open mode can list users and approve/deactivate accounts with an anonymously obtainable anti-forgery token. Open-mode clients can also reach global settings, background jobs, and the [deployment endpoint](../../server/src/MediaDock.Api/Operations/DeploymentControlEndpoints.cs) if its host socket is configured. Anti-forgery tokens are not identity or authorization. Personal favorites, ignored titles, ratings, and recommendations remain owner-scoped even in open mode.

**Action:** complete the HTTPS callback and first-admin bootstrap in the protected environment, then deploy `GOOGLE_AUTH_ENABLED=true`, an exact HTTPS callback, and `ACCESS_CONTROL_ENFORCED=true` together with fail-closed startup/config checks for internet-facing use. Keep a host-only recovery procedure; never switch back to open mode to recover an account. Test anonymous, unlinked, pending, deactivated, active user, and admin identities against every endpoint group and direct API requests. Consider removing open mode entirely after migration.

### A2. UI gate improved locally; asset delivery is still public (medium)

[App.tsx](../../web/src/App.tsx) now sets an access gate until an active linked account is present and renders a welcome/sign-in view for anonymous visitors. The dirty worktree's [App tests](../../web/src/App.test.tsx) assert that anonymous routes do not show catalog screens or navigation; all 36 focused tests passed on 2026-10-30. This is a meaningful improvement over the 2026-10-26 source, but it is not committed or deployed evidence. In addition, production [Program.cs](../../server/src/MediaDock.Api/Program.cs) still serves `index.html`, JavaScript, and CSS through static-file/fallback middleware without an active-user check. That makes the client implementation downloadable, but does not itself expose private data if API authorization is correctly enforced. The public welcome view also contains brief product copy, not literally only a sign-in control.

**Action:** verify the current active-account UI gate, commit and deploy it, and confirm the anonymous welcome/sign-in view, unmatched registration flow, and pending/deactivated account states. Clear owner-scoped client state on sign-out/account change. Continue to treat API authorization as the security boundary. A browser necessarily downloads the assets needed to render its current page; protect the application bundle at the server/edge only if the requirement is to conceal implementation code, not merely to hide app screens and data. Keep health checks internal and avoid making `/api/version` publicly visible if the edge is configured for login-only access.

### A3. Edge and origin bypass (blocker)

The [Compose API port](../../compose.yaml) is loopback-bound by default, but the documented LAN deployment uses a specific host interface and [DOCKER-USER allowlist](../../deploy/firewall/mediadock-next-docker-user.sh). The [systemd runbook](../../deploy/systemd/README.md) describes an HTTPS Cloudflare Tunnel on a dedicated bridge and an Access challenge observed in October 2026; direct non-LAN denial/router port-forward checks were still unverified. The origin and LAN API speak HTTP. Cloudflare Access authenticates traffic that passes through its policy, not direct host-port or other-hostname traffic, and does not assign MediaDock account roles.

**Action:** verify the live deployed SHA, Compose binds, Docker network memberships, host and upstream router rules, all public DNS/hostnames, and Access policy coverage for `/`, `/api/*`, `/signin-oidc`, static assets, and alternate routes. From an external network, test denial for direct host IP:port and every bypass hostname; from an untrusted LAN source, test firewall denial. Do not publish PostgreSQL. Restrict the API origin to the Tunnel plus an explicitly trusted admin path, or remove LAN access if unnecessary. HTTPS must terminate at the edge with the exact callback URI; keep forwarded-proto trust limited to the dedicated Tunnel CIDR, never a wildcard/default Docker network. Decide whether the Cloudflare Access challenge is the first login screen or whether an allowed SSO flow presents the MediaDock Google button; test the full redirect/cookie journey without bypass rules that leave `/api/*` open.

### A4. Exception detail disclosure (high)

[ApiExceptionHandler.cs](../../server/src/MediaDock.Api/Middleware/ApiExceptionHandler.cs) places `exception.Message` in the 500 `ProblemDetails.Detail`. Exceptions from a database, provider, or host socket can include internal details. **Action:** respond with a fixed generic 500 message and trace ID; log the exception in the protected server log only. Add a test that raises a synthetic exception and verifies its sentinel message is absent from the response.

### A5. Anti-forgery coverage (high)

Cookie authentication and a token endpoint exist in [GoogleSignInOptions.cs](../../server/src/MediaDock.Api/Authentication/GoogleSignInOptions.cs) and [AuthenticationEndpoints.cs](../../server/src/MediaDock.Api/Authentication/AuthenticationEndpoints.cs). Linking, registration, logout, user approval/status, personal-rating import/enrichment, and marking a recommendation watched explicitly validate tokens. The personal-ratings upload disables framework antiforgery metadata but performs an explicit token check in its handler. In contrast, admin dataset uploads disable automatic antiforgery without an equivalent handler check. Other cookie-authorized mutations without explicit token validation include favorites and ignored-title changes, system/recommendation settings, job dispatch, deployment actions, operational-history deletion, and Golden Globes IMDb linking. `SameSite=Lax` on the session cookie limits many cross-site POSTs, but is not a substitute for a consistent policy, particularly for same-site sibling origins or future hosting changes. This finding is a missing defense; this audit has **not** demonstrated a working cross-origin exploit.

**Action:** inventory every non-safe HTTP method, including multipart and settings changes; require token validation (or equivalent robust origin/CSRF defense) for every cookie-authenticated mutation. Align [client.ts](../../web/src/api/client.ts) token submission, add cross-site/same-site negative tests, and keep authorization checks independent of CSRF. Give imports per-route size/content limits and retain existing owner/admin constraints.

### A9. Development mock authentication behind the Vite proxy (conditional high)

The new [Development mock handler](../../server/src/MediaDock.Api/Authentication/LocalMockAuthenticationHandler.cs) correctly requires `Development`, a loopback database, and a loopback immediate peer; service registration rejects the setting in Production. The [restored-data launcher](../../scripts/run_local_restored.ps1) enables that scheme, enforces access control, disables the dispatcher, binds the API to `localhost:5280`, and targets a restored production database. The [Vite config](../../web/vite.config.ts) proxies `/api` requests to that API. If Vite is deliberately or accidentally run with a LAN/public bind (for example `--host 0.0.0.0`), the API sees the local Vite process as its peer, not the remote browser, and the mock handler can authenticate the proxied request as the sole active user. Vite's normal default is local-only, and the launcher does not start Vite; this is a conditional local-development exposure, not a production-mode authentication bypass. The current mock-auth tests cover the environment and database guards but not the proxy topology.

**Action:** never expose or tunnel the Vite server while using a restored production database with mock auth. Keep the dev server bound to loopback, and use sanitized local data or real authentication for any shared development environment. Verify ports `5173` and `5280` are not reachable from untrusted interfaces before opening restored production data.

### A6. Abuse and resource exhaustion (high)

The [API composition](../../server/src/MediaDock.Api/Program.cs) configures no rate-limiting middleware; [auth endpoints](../../server/src/MediaDock.Api/Authentication/AuthenticationEndpoints.cs) issue anti-forgery tokens and allow registration requests; [background-job endpoints](../../server/src/MediaDock.Api/BackgroundJobs/BackgroundJobEndpoints.cs) accept bounded uploads and queue costly work. [RSS transport](../../server/src/MediaDock.Infrastructure/Rss/RssFeedTransport.cs) already restricts destination, redirects, XML, and response size, but those safeguards do not rate-limit incoming traffic or all database-heavy searches.

**Action:** set route-specific edge/app quotas for auth/session/token and registration traffic, anonymous health, expensive reads, uploads, and job dispatch. Limit concurrent jobs and request bodies; use trusted-proxy source information correctly rather than blindly trusting client-supplied forwarding headers. Measure false positives for shared IPs and test 429 responses and recovery.

### A7. Browser and cache policy (medium)

No explicit CSP, HSTS, frame-ancestor, MIME-sniffing, referrer, or permissions policy is set in reviewed [Program.cs](../../server/src/MediaDock.Api/Program.cs), and only the anti-forgery token endpoint explicitly sets `Cache-Control: no-store`; edge headers were not inspected. React escapes rendered text, and the reviewed web source contains no `dangerouslySetInnerHTML`, but a browser XSS defense remains valuable. The [title details link](../../web/src/features/catalog/TitleDetailsDialog.tsx) also renders a feed-derived outbound URL; review URL validation at the ingestion and display boundary.

**Action:** enforce HTTPS/HSTS at the public edge after verifying host coverage; add `Content-Security-Policy` (trial in report-only first), `frame-ancestors 'none'`, `X-Content-Type-Options: nosniff`, a conservative referrer/permissions policy, and `Cache-Control: no-store` for private API/session responses. Validate supported outbound-link schemes and use `noopener noreferrer` for new tabs. Confirm actual edge headers and the OIDC flow in browsers before enforcement.

### A8. Operational security and supply chain (medium)

[GoogleSignInOptions.cs](../../server/src/MediaDock.Api/Authentication/GoogleSignInOptions.cs) uses a 12-hour, non-sliding, HttpOnly, Secure, `__Host-` cookie, code flow with PKCE, signed-token validation, and no saved provider tokens. [AccessControl.cs](../../server/src/MediaDock.Api/Authentication/AccessControl.cs) resolves active state and current role from PostgreSQL on each protected request. [Compose](../../compose.yaml) keeps PostgreSQL on loopback; the [API image](../../server/Dockerfile) runs as a non-root user. These are positive controls, not substitutes for access enforcement.

No explicit persisted ASP.NET Data Protection key-ring configuration is visible in the reviewed API/Compose path; verify where keys live in the running container and persist them securely so restart/replica changes do not silently invalidate cookies. The [security guide](SECURITY.md) notes the OMDb key is plaintext in PostgreSQL/backups and the ignored `.env` contains host secrets. The [Dockerfile](../../server/Dockerfile) and [Compose](../../compose.yaml) use version tags for application build/base images and PostgreSQL; the [deployment gate](../../deploy/test.sh) runs tests but does not run dependency advisories. The current advisory checks found no reported vulnerable dependencies, but container/OS CVEs, secret leakage, and restored-backup integrity were not assessed.

**Action:** verify key-ring storage, encryption/permissions, secret and backup access, credential rotation, least-privilege database roles, patch cadence and pinned/reviewed image digests, image scanning, and backup restore drills on the host. Keep the bootstrap identity values host-only and remove them after provisioning. Review who can push `main`, run the root-equivalent Docker test gate, or trigger the root-backed deployment socket. Protect and monitor audit logs for admin approvals, role/status changes, imports, and deployments without logging credentials or cookies.

## Deployment sequence and acceptance gates

1. **Prepare privately:** inspect the running SHA, outstanding migrations and backup/restore readiness; verify the live Tunnel, Access rule, router, firewall, Docker bridge, and direct-origin denial. Keep the existing perimeter in place throughout rollout. Host migration and deployment require separate operator approval.
2. **Establish identity:** provision the exact HTTPS Google callback and trusted forwarded-proto CIDR, enable Google sign-in inside the protected route, verify OIDC callback/session, bootstrap the first active administrator using a validated session identity, and remove bootstrap values. Choose approved users/registration policy; an arbitrary verified Google account must never imply app access.
3. **Close app access:** enforce active-account API authorization and fail-closed deployment settings; verify, commit, and deploy the current active-account UI gate. Keep the Vite mock-auth workflow loopback-only and out of shared/exposed environments. Gate app assets only if implementation-code confidentiality is required. Fix error disclosure and CSRF gaps, then add rate limits and headers. Preserve explicit, narrowly scoped login/health exceptions.
4. **Exercise the matrix:** from a clean external browser and direct HTTP client, verify anonymous users see only the intended login/protocol surface; `/api/catalog`, `/api/admin/users`, `/api/deployment`, imports, personal data, and every other protected route return 401. Unknown, pending, and deactivated users must not read app data; active users must get 403 on admin routes; admins must work. Verify registration approval, role change, sign-out, CSRF rejection, upload bounds, rate limits, cookie security, private cache headers, and full Access-to-Google redirect flow. Recheck origin bypass from off-LAN and post-redeploy.
5. **Go/no-go:** do not widen exposure until all blocker fixes, high-severity controls, affected integration/web tests, backup restore, external deny tests, and operator review pass on the **deployed SHA**. Record dated host/Cloudflare evidence; repeat after network/auth configuration changes. This document alone is not authorization to change production settings.

## Remaining verification

This reassessment did not confirm Cloudflare policy specificity, other public DNS/routes, TLS configuration, HTTP response headers, installed image/kernel CVEs, key-ring location, actual firewall/port-forward state, production migration status, restored-backup integrity, or application behavior at the public hostname. It did not execute adversarial CSRF, SSRF, XSS, or load tests, and did not verify actual listener exposure for the local Vite workflow. Those checks are required for a full operational security sign-off; a clean source review and passing focused tests cannot replace them.
