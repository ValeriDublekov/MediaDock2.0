# План за подобрения

**Дата на прегледа:** 2026-09-30  
**Статус:** исторически преглед от 2026-09-30; Worker/runtime предложенията са superseded от реализирания [background ingestion plan](BACKGROUND_INGESTION_PLAN.md)

## Обхват и отправна точка

Статичен преглед на API, Worker, React клиента, тестовете, Compose, deployment gate и оперативните инструкции. Не е извършвано разгръщане, сканиране на RSS/OMDb, промяна на данни или изпълнение на тестовете. Съществуващите [преглед на модела](DATABASE_MODEL_REVIEW.md) и [Oscar план](OSCAR_CATALOG_PLAN.md) не се отварят повторно като нови задачи: базовата миграция и Oscar каталогът вече са реализирани според [текущия статус](IMPLEMENTATION_STATUS.md).

## P0: оперативни проверки преди разширяване на достъпа или сканиране

1. **Потвърждаване на мрежовата граница в реалната среда.** [Оперативният runbook](../../deploy/systemd/README.md) отчита успешни LAN заявки, но проверките за липса на router port-forward и отказ от нетръстната мрежа остават неизпълнени. Направете ги с оператора, запишете дата, източник на теста и резултат без реални адреси/подмрежи в Git. До тогава не приемайте LAN smoke test за доказателство за изолация. **Приемане:** от разрешената мрежа API е достъпен, от забранена не е; няма неочакван външен път до порта.
2. **Изпробване на възстановяване от backup в изолирана база.** [Backup процедурата](../../README.md) и [host runbook-ът](../../deploy/systemd/README.md) имат dump, retention и `pg_restore -l`, но проверка на архива не доказва, че приложението тръгва с възстановени данни. Изпълнете тестово restore без продукционни записи в логовете; проверете миграционната история, `/health/ready` и основните заявки; документирайте време за възстановяване и подход за ключа в dump-а. **Приемане:** последен архив може да бъде възстановен и прочетен в отделна среда, без докосване на продукционната БД.
3. **Контролиран manual scan след изрично одобрение.** След production cutover, проверка на OMDb ключа, общата дневна квота и включените feeds, договорете единичен ръчен job през Configuration и проверете [scan history и UTC budget](../../README.md). Scheduler activation остава отделно операторско решение. **Приемане:** операторът е одобрил външните заявки и разхода на квота; job, scan history и броячите съответстват на пуска.

## P1: надеждност и поддръжка

4. **Readiness да отразява приложимостта на схемата.** [ReadinessService](../../server/src/MediaDock.Api/Health/ReadinessService.cs) проверява само `CanConnectAsync`; API може да върне 200 с база без очакваната миграция. Добавете проверка за очакваната схема/миграция с ограничено време, без да мигрирате при API startup; оставете `/health/live` само за процеса. Покрийте празна, стара и актуална схема с изолирани API integration тестове; използвайте резултата и в deploy smoke check, без да променяте loopback/specific-interface bind-а. **Приемане:** readiness е 503 при несъвместима схема и 200 при актуална; deploy не маркира такава версия за успешна.
5. **Диагностика и interrupted recovery за API jobs.** [BackgroundJobDispatcher](../../server/src/MediaDock.Api/BackgroundJobs/BackgroundJobDispatcher.cs) записва safe error codes/events и маркира изоставени `running` jobs `interrupted` след restart; автоматичен retry няма. Остава полезно бъдещо подобрение да се добавят изолирани failure/cancellation tests за тези пътища, без да се логват OMDb ключ, пълен outbound URL или connection string. **Приемане:** отказ се диагностицира от safe events/job history без чувствителни стойности.
6. **Единен собственик на правилата за feed URL.** [SourceSettingsApiService](../../server/src/MediaDock.Api/Sources/SourceSettingsApiService.cs) проверява URL при запис, а [RssFeedTransport](../../server/src/MediaDock.Infrastructure/Rss/RssFeedTransport.cs) го валидира при извличане. Изведете общите правила за допустим URL в споделена политика с тестове за граничните случаи; запазете повторната проверка в транспорта, както и неговите DNS/redirect/SSRF защити. **Приемане:** API отказва URL, който транспортът би отхвърлил по статичните правила; транспортът не разчита на предходна API валидация.
7. **Политика за растежа на оперативните таблици.** [Прегледът на модела](DATABASE_MODEL_REVIEW.md) вече отбелязва `parse_logs` и `scan_runs`. Измерете реалния обем и темп след първите одобрени сканирания; задайте срок за съхранение и backup/архивиране, преди да добавяте автоматично изтриване. Проверете и пагинацията при реалистичен обем. **Приемане:** документиран срок и възстановимост; всяка бъдеща cleanup задача има тест за границите на изтриване.

## P2: maintainability и качество на промените

8. **Разделяне на отговорностите при настройките.** [SourceSettingsApiService](../../server/src/MediaDock.Api/Sources/SourceSettingsApiService.cs) събира CRUD за източници, matching настройки и OMDb ключ/лимити. При следваща промяна в тези потоци отделете услугите по функция, без нов проект или изкуствен Application слой; запазете атомарното създаване на singleton settings и редакцията на ключа без връщане на стойността му. **Приемане:** всяка услуга има ясна причина за промяна, а съществуващите API contract/integration тестове за трите потока продължават да минават.
9. **Единствен API composition root.** Изпълнено от background ingestion имплементацията: API регистрира Infrastructure adapters и hosted dispatcher; самостоятелният Worker entry point премахнат. Оставащата проверка е да се поддържат handler-ите/test-овете фокусирани при бъдещи промени.
10. **Фокусирани тестове за operational paths.** Background-job producer, upload persistence, hosted import, Sofia DST/catch-up, advisory lock и ingestion UI вече имат целеви тестове. Оставащ gap: допълнителни автоматизирани проверки за API migration-only hosted-service suppression, interrupted recovery/cancellation и concurrent queue claim, както и отделен `HistoryView` test. Няма тест, който да извиква live feed/OMDb.
11. **По-ранна обратна връзка за pull requests.** Наличният [staging gate](../../deploy/test.sh) пуска web lint/test/build, .NET unit/integration и image build на чист доверен commit на Ubuntu host; в репото няма GitHub workflow за PR. Обмислете ограничен PR gate за web и .NET unit/build без production secrets и без Docker socket; запазете host gate за Testcontainers, Compose и deploy. Преди автоматично публикуване от `main` договорете защита на branch-а/одобрение на промени в миграции и deploy scripts. **Приемане:** лош PR се отхвърля преди merge, а съществуващият host gate остава задължителен и изолиран от production `.env`/volumes.
12. **Поддръжка на документацията като проверима част от доставката.** [Статусът на имплементацията](IMPLEMENTATION_STATUS.md) още описва backup retention като липсващ, а [host runbook-ът](../../deploy/systemd/README.md) вече описва активен backup timer и 14 дневни dump-а. Сверете статуса с реалните units и допълнете [тестовата стратегия](TESTING.md) с Oscar API/frontend тестовете. **Приемане:** таблицата за shipped/limitations и примерните тестови команди не противоречат на текущите runbooks и файлове.
13. **Малко BE почистване при следващ подходящ PR.** Празният Worker scaffold е премахнат с проекта; празният `Application/Class1.cs` и общата pagination helper остават отделен, unrelated cleanup. Не въвеждайте нов framework без реална нужда.

## Ред и ограничения

- Първо P0 проверките; те са операторски задачи и не изискват нов код. След това P1 readiness, диагностика и единна URL политика. P2 разделянето се прави на малки стъпки с тестове за съществуващото поведение, после PR gate и документация. Retention и performance оптимизации се основават на измервания, не на предположения.
- Не добавяйте authentication или интернет експозиция като страничен ефект от този план. Ако достъпът напусне доверения LAN, отделен security дизайн с identity, TLS, роли и audit е предпоставка, а не малка настройка на Compose.
- За кодови промени използвайте [изолираните тестове](TESTING.md) и чистия server-side gate; никога не използвайте ръчен API scan като тест. Продукционен reset, първи manual/scheduled job или промяна на firewall изискват отделно разрешение от оператора.
