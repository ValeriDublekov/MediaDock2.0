# API: Identity and Personal Data

Task router for Google sign-in, account linking and administration, favorites, ignored titles, and personal IMDb ratings. Shared paging, errors, and access modes are in [API contracts](API_CONTRACTS.md); cross-layer flow is in [Architecture](ARCHITECTURE.md).

## Client-visible and security rules

- Google identity and email are trusted only after server validation. Linking and registration use validated identity claims, not client-supplied account data; sign-in accepts any Google account with a verified email and has no domain allowlist. Registration requires an explicit user action.
- The API resolves the provider identity to the current account status and role in the database. Bootstrap is a host-only Compose operation; its operator must use identity values from an authenticated session response because the bootstrap tool does not validate Google claims. See the [local operations runbook](../../README.md).
- Favorites, ignored titles, ratings, imports, and personal-rating enrichment always require an active linked user and are scoped to that user, even when general access enforcement is disabled. Client-supplied owner IDs are ignored; administrators see only their own personal data. Open mode does not make personal routes public. See [access modes](API_CONTRACTS.md#access-modes).
- Favorites use IMDb identity, not a catalog or award-source row ID. `POST /api/favorites` accepts `imdbId` and `from`; it succeeds only for an existing enriched IMDb movie. Repeated adds from Oscar and catalog views merge into the same `(user_id, imdb_id)` favorite. `PATCH` and `DELETE /api/favorites/{imdbId}` use the same owner-scoped key.
- Ignored titles use the same canonical IMDb identity across catalogs and recommendations. `POST /api/ignored-movies` accepts only `imdbId` for an existing enriched IMDb movie or series; the API resolves the owner from the active linked account. `GET /api/ignored-movies` lists only that owner's records, and `DELETE /api/ignored-movies/{imdbId}` removes only that owner's record. Catalog and recommendation results exclude ignored IDs before counting and paging.
- `ToDownload` is a future-search marker and does not require an existing torrent release. Unmatched records and IMDb rows whose metadata is pending or unsuccessful cannot be added; favorite controls are only offered for enriched movie matches.
- Personal-rating import is an owner-scoped merge, not a replacement: IDs omitted from a later file remain stored. The JSON is processed in memory, not saved as an uploaded file.
- `GET /api/recommendations` always requires an active linked user, including when access enforcement is disabled. The server resolves the owner from validated identity; it does not accept a client-supplied user ID. Results select `movie` (the default) or `series` and exclude that user's ignored and rated titles; movie `ToWatch` entries are also excluded, while `ToDownload`-only movies remain eligible.
- `POST /api/recommendations/{imdbId}/watched` requires an active linked user, a valid anti-forgery token, and an integer rating from `1` to `10`. The optional `mediaType` body value defaults to `movie`; use `series` for a series recommendation. The server rechecks eligibility and creates an owner-scoped `personal_ratings` row with `is_manually_added = true`; it does not accept a client-supplied owner ID. The personal-ratings response exposes `isManuallyAdded`; new imported rows use `false`, and import updates preserve the existing marker.
- `GET` and `PUT /api/settings/recommendations` and `POST /api/settings/recommendations/recalculate-votes` use the administrator policy when enforcement is enabled. They manage global settings, not user preferences; open mode leaves them unprotected and does not change the configured network boundary.

## Recommendation Settings

- `GET /api/settings/recommendations` returns the median period, Bayesian prior settings, four source-level award defaults, category overrides, vote-recalculation dirty state, and last-success metadata.
- `PUT /api/settings/recommendations` accepts those global values and category override rows. The period must be positive, `bayesian_default_c` must be in `[0,10]`, `bayesian_m_ratio` in `(0,1]`, and award points must be nonnegative. Changing the period marks vote weights dirty; Bayesian or award-point changes do not require vote-weight recalculation.
- `POST /api/settings/recommendations/recalculate-votes` recalculates synchronously and returns the calculation time, duration, period, movie/vote counts, and fallback-median count. The API has a 10-second execution limit; a 504 timeout leaves the dirty flag set and the web warning visible.
- The settings page displays “New metadata detected. Recommended scores may be inaccurate. Recalculate vote weights.” while the dirty flag is true. If recalculation later returns `202 Accepted`, the page polls settings until the flag is false; the current endpoint returns `200 OK` for synchronous completion.

## Personal Recommendations

- `GET /api/recommendations` uses the shared `PageResponse<T>` contract: `page` defaults to `1`, `pageSize` defaults to `25`, and the maximum page size is `100`. Optional `mediaType` is `movie` or `series` and defaults to `movie`.
- Optional inclusive `yearFrom`/`yearTo` and repeatable `genres` query values filter candidates before counting and paging. A title matches any selected genre; the response's year bounds describe the active user's eligible candidates of the selected type before these filters.
- `GET /api/recommendations/genres?mediaType=...` returns sorted distinct genre values for the selected IMDb title type (`movie` by default) and requires an active linked user under the recommendation access policy.
- Every request must provide `ratingWeight`, `votesWeight`, and `awardsWeight`. Each is in `[0,1]` and their decimal sum must equal `1.0`. The web client's first-use values are `0.50`, `0.25`, and `0.25`, respectively; they remain in client/request state and are not persisted by the API.
- The recommendations page uses three integer-percent sliders, redistributes the remainder when one changes, and sends coefficients totaling exactly `1.0` with every paged request. Changing pages keeps the current coefficients and filters; changing a filter resets the page to `1`, and reopening the view starts from the approved defaults.
- The web exposes separate Movie recommendations and Series recommendations navigation items backed by the same view; the legacy `/account/recommendations` route redirects to movies.
- Movie candidates are enriched canonical IMDb movie rows with a non-empty title, a non-null IMDb rating, and an Oscar or qualifying Golden Globes nomination linked by IMDb ID. Series candidates require a qualifying Golden Globes series nomination whose nominee type and canonical IMDb media type are both `series`; Oscars are movie-only. Torrent-only, unmatched, pending, incomplete-title, and missing-rating records are excluded.
- The rating component uses the configured Bayesian prior and the selected type's era-specific vote median; popularity uses logarithmically scaled, capped vote ratios. Movie popularity weights are persisted and recalculated by the settings workflow; series weights use the same normalizer at request time. Taste multipliers use rated awards for the selected type, and award events use win or nomination defaults with optional category overrides. See the [movie and series recommendation engine reference](MOVIE_RECOMMENDATION_ENGINE.md) for formulas and fallbacks.
- Results sort by final score descending, then IMDb ID ascending. Each item includes title data, normalized score components, applied coefficients, final score, and distinct contributing award events with source, category, outcome, base points, taste multiplier, and adjusted points. Award events expose Oscar ceremony numbers separately from Golden Globes ceremony years.
- The web renders the result page and score/event breakdown returned by the API; it does not rescore candidates, fetch catalog rows for recommendation candidates, or persist the coefficients.
