# Persistence And Data Contracts

This document covers PostgreSQL persistence in `server/`. For HTTP projections see [API contracts](API_CONTRACTS.md); for runtime flow see [Architecture](ARCHITECTURE.md).

## Schema And Entities

[`MediaDockDbContext`](../../server/src/MediaDock.Infrastructure/Persistence/MediaDockDbContext.cs) exposes fifteen sets and applies entity configurations from the Infrastructure assembly. Entity property-to-column mappings and constraints live in [CatalogConfigurations.cs](../../server/src/MediaDock.Infrastructure/Persistence/Configurations/CatalogConfigurations.cs), [OperationalConfigurations.cs](../../server/src/MediaDock.Infrastructure/Persistence/Configurations/OperationalConfigurations.cs), [BackgroundJobConfigurations.cs](../../server/src/MediaDock.Infrastructure/Persistence/Configurations/BackgroundJobConfigurations.cs), [SettingsConfiguration.cs](../../server/src/MediaDock.Infrastructure/Persistence/Configurations/SettingsConfiguration.cs), [MetadataCacheConfiguration.cs](../../server/src/MediaDock.Infrastructure/Persistence/Configurations/MetadataCacheConfiguration.cs), [OscarConfigurations.cs](../../server/src/MediaDock.Infrastructure/Persistence/Configurations/OscarConfigurations.cs), [FavoriteMovieConfiguration.cs](../../server/src/MediaDock.Infrastructure/Persistence/Configurations/FavoriteMovieConfiguration.cs), [OscarEnrichmentRunConfiguration.cs](../../server/src/MediaDock.Infrastructure/Persistence/Configurations/OscarEnrichmentRunConfiguration.cs), and [OmdbDailyUsageConfiguration.cs](../../server/src/MediaDock.Infrastructure/Persistence/Configurations/OmdbDailyUsageConfiguration.cs). PostgreSQL schema history includes the generated baseline [20260930122500_InitialRelationalSchema.cs](../../server/src/MediaDock.Infrastructure/Persistence/Migrations/20260930122500_InitialRelationalSchema.cs), additive [AddFavoriteMovies](../../server/src/MediaDock.Infrastructure/Persistence/Migrations/20260930160830_AddFavoriteMovies.cs), [AddBackgroundJobs](../../server/src/MediaDock.Infrastructure/Persistence/Migrations/20261001114648_AddBackgroundJobs.cs), [AssociateParseLogsWithScanRuns](../../server/src/MediaDock.Infrastructure/Persistence/Migrations/20261001114926_AssociateParseLogsWithScanRuns.cs), and [AllowBackgroundJobPayloadCleanup](../../server/src/MediaDock.Infrastructure/Persistence/Migrations/20261001115421_AllowBackgroundJobPayloadCleanup.cs), plus the current [model snapshot](../../server/src/MediaDock.Infrastructure/Persistence/Migrations/MediaDockDbContextModelSnapshot.cs). The baseline replaces the six earlier migrations; a database with their `__EFMigrationsHistory` requires an explicit per-environment reset before this baseline can be applied (see the [systemd runbook](../../deploy/systemd/README.md#one-time-baseline-reset)). The API applies migrations and exits when configured with `migrate = true` ([Program.cs](../../server/src/MediaDock.Api/Program.cs)).

Its title FK uses `RESTRICT`; `ck_favorite_movies_origin` requires at least one selected source. Source availability and movie media type are checked by the API at insertion; the origin flags persist independently of later imports/observations. The API uses `INSERT ... ON CONFLICT` for concurrent additions, adding the new source's default marker without resetting user selections from an existing source. Neither RSS nor Oscar import writes to `favorite_movies`.

## Keys And Constraints

Background jobs and events use generated `bigint` primary keys; scheduler state is keyed by its schedule name. Other generated table IDs follow the existing schema conventions. The alternate unique keys and indexes are:

| Constraint | Unique columns | Purpose |
| --- | --- | --- |
| `ak_sources_stable_key` | `sources.stable_key` | Stable source identity. |
| `ak_occurrences_source_id_source_item_key` | `occurrences.source_id`, `occurrences.source_item_key` | One occurrence identity per source. |
| `pk_rss_item_states` | `rss_item_states.source_id`, `rss_item_states.source_item_key` | One fingerprinted processing state per feed item. |
| `ak_metadata_cache_cache_key` | `metadata_cache.cache_key` | One metadata-cache row per resolver key. |
| `ux_titles_imdb_id` | `titles.imdb_id` (partial: non-null and nonblank) | One canonical title per normalized IMDb ID. |
| `ux_oscar_films_stable_key` | `oscar_films.stable_key` | One Oscar candidate per IMDb ID, or normalized title/year fallback. |
| `ux_oscar_nominations_import_key` | `oscar_nominations.import_key` | One source nomination per ceremony/category/film/nominee/detail identity. |
| `ux_background_jobs_scheduled_slot_utc` | `background_jobs.scheduled_slot_utc` (partial: non-null) | Idempotent scheduled enqueue per UTC slot. |
| `ux_background_jobs_active_rss_scan` | `background_jobs.job_type` (partial: RSS and queued/running) | At most one active RSS scan. |
| `ux_background_jobs_active_oscar_enrichment` | `background_jobs.job_type` (partial: Oscar enrichment and queued/running) | At most one active Oscar enrichment job. |
| `ux_background_jobs_scan_run_id` | `background_jobs.scan_run_id` (partial: non-null) | One RSS job association per scan run. |

IMDb IDs are trimmed and lowercased at CSV and OMDb boundaries; blank values become `NULL`. The `ux_titles_imdb_id` partial unique index permits multiple missing IDs but rejects duplicates. The title fallback index is deliberately non-unique: `ix_titles_normalized_title_year_media_type` allows different films with the same normalized title, year, and media type. Application fallback matching links an existing title only when its IMDb ID is absent or compatible with the incoming ID; it never merges two different non-null IDs.

`settings` is a singleton row with `CHECK (id = 1)`. The API-hosted dispatcher reads only key `1`; first creation uses that explicit key and retries a concurrent primary-key winner. There is no lowest-ID convention.

`rss_item_states.source_id` references `sources.id` with `RESTRICT`; `ix_rss_item_states_expires_at` supports expiry maintenance.

Foreign keys include `occurrences.title_id -> titles.id`, `occurrences.source_id -> sources.id`, nullable `parse_logs.source_id -> sources.id`, nullable `parse_logs.scan_run_id -> scan_runs.id`, nullable `background_jobs.scan_run_id -> scan_runs.id`, `background_job_events.job_id -> background_jobs.id`, `oscar_films.title_id -> titles.id`, and `oscar_nominations.oscar_film_id -> oscar_films.id`. They use `RESTRICT` except job events, which cascade when a job is deleted. Other non-unique indexes include `ix_titles_normalized_title_year_media_type`, `ix_occurrences_title_id_last_seen_at`, `ix_scan_runs_started_at`, `ix_parse_logs_processed_at`, `IX_parse_logs_source_id`, `ix_background_jobs_status_enqueued_at`, `ix_background_job_events_job_id_id`, `ix_metadata_cache_expires_at`, `ix_oscar_films_film_year`, and `ix_oscar_nominations_category_ceremony`.

Database check constraints enforce:

- `ck_sources_feed_type` restricts `sources.feed_type` to `movie`, `series_complete`, or `series_ongoing`; both series modes are treated as OMDb `series` and source years are treated as season/episode years, not show premiere years.
- `ck_rss_item_states_disposition` restricts item state to `resolved` or `terminal`; `ck_rss_item_states_expiry` requires terminal decisions to have an expiry and permits temporary expiry on adopted legacy resolved entries.
- `ck_titles_media_type` restricts `titles.media_type` to `movie`, `series`, `documentary`, or `short`; `ck_titles_source_type` restricts nullable `source_type` to `movie` or `series`; `ck_titles_content_kind` restricts nullable `content_kind` to `standard`, `documentary`, or `short`.
- `ck_titles_seen_range` requires `titles.first_seen_at` and `titles.last_seen_at` to be both null or both set with `first_seen_at <= last_seen_at`; these fields represent torrent observations, not Oscar import or metadata enrichment. `ck_occurrences_seen_range` requires `occurrences.first_seen_at <= occurrences.last_seen_at`.
- `ck_scan_runs_status` restricts `scan_runs.status` to `running`, `succeeded`, `partial`, or `failed`; `ck_scan_runs_trigger` restricts `trigger` to `schedule`, `manual`, or `local`.
- `ck_scan_runs_finish_time` requires `running` rows to have a null `finished_at` and every completed status to have a non-null value.
- `ck_background_jobs_type`, `ck_background_jobs_trigger`, and `ck_background_jobs_status` restrict job types, triggers, and lifecycle statuses; `ck_background_jobs_type_trigger` permits scheduled RSS only and manual Oscar jobs only.
- `ck_background_jobs_lifecycle` enforces queued/running/terminal timestamp shape. `ck_background_jobs_input_type` requires queued/running Oscar imports to retain bytes and permits cleanup after terminal state; RSS jobs never store upload bytes.
- `ck_oscar_films_enrichment_status` restricts the enrichment status to `pending`, `enriched`, `not_found`, or `temporary_error`; `ck_oscar_films_enrichment_attempt_count` requires a non-negative attempt count.
- `ck_oscar_enrichment_runs_status` restricts Oscar run status to `running`, `succeeded`, `partial`, `quota_stopped`, `failed`, or `cancelled`; `ck_oscar_enrichment_runs_trigger` allows `manual` and `schedule`; `ck_oscar_enrichment_runs_counts` requires non-negative progress counters.
- `ck_oscar_enrichment_runs_finish_time` requires `running` rows to have a null `finished_at` and every completed status to have a non-null value.
- `ck_settings_singleton_id` restricts `settings.id` to `1`.
- `ck_settings_min_movie_rating` and `ck_settings_min_series_rating` restrict ratings to 0 through 10; `ck_settings_min_imdb_votes` restricts votes to 0 through 1,000,000,000.
- `ck_settings_omdb_daily_request_limit` requires a non-negative shared limit; `ck_settings_oscar_max_films_per_run` caps the candidate setting at 100,000; `ck_settings_oscar_max_requests_per_day` requires a non-negative Oscar cap.
- `ck_parse_logs_retry_state` restricts `parse_logs.retry_state` to `retryable`, `terminal`, or `resolved`; `ck_parse_logs_attempt_count` requires `attempt_count >= 0`.
- `ck_metadata_cache_status` restricts status to `found` or `confirmed_not_found`; `ck_metadata_cache_expiry` requires `expires_at > fetched_at`.
- `ck_omdb_daily_usage_counts` requires non-negative counts and `oscar_requests <= total_requests`.

The `SystemSourceProfiles` migration preserves each RSS URL, replaces stored source names with fixed profile labels, activates configured URL rows, and maps any legacy `series` values in sources, occurrences, or parse logs to `series_ongoing`. Removing a URL through the API disables its `sources` row rather than deleting it because occurrences, parse logs, and RSS item states retain its ID.

The schema does not define an optimistic concurrency token. The unique IMDb key is database-enforced, while title/year matching remains a guarded application fallback and is intentionally non-unique.

## Idempotency And Transactions

RSS item processing uses `rss_item_states`, keyed by source and `SourceItemIdentity`, separately from `metadata_cache`. Its SHA-256 fingerprint covers the raw title, torrent URL, publication timestamp, feed mode, parser version, and matching exclusions. New resolved items skip metadata lookup indefinitely while refreshing occurrence/title `LastSeenAt`; terminal decisions expire after two days. At rollout, unchanged prior occurrences and recent terminal logs are adopted for two days, then retried under the current parser. A changed fingerprint is reprocessed. `scan_runs.known_entries_skipped` distinguishes these skips from entries ignored by matching; `entries_seen` remains all feed entries read, and `omdb_requests` counts actual HTTP attempts.

[`OscarDatasetImporter`](../../server/src/MediaDock.Infrastructure/OscarAwards/OscarDatasetImporter.cs) reads compact comma-separated exports or the original tab-separated Kaggle file and filters to `Year > yearAfter` plus exactly `BEST PICTURE`, `DIRECTING`, `WRITING (Original Screenplay)`, `WRITING (Adapted Screenplay)`, and `CINEMATOGRAPHY`. It normalizes IMDb IDs, matches `titles` by IMDb ID first, then uses normalized title/year only when the IDs do not conflict; otherwise it creates a distinct title placeholder. Oscar-only placeholders have null `FirstSeenAt`/`LastSeenAt`. Re-import preserves populated title metadata and enrichment status, upserts film and nomination rows in one transaction, and never creates `occurrences` or contacts OMDb. Nomination identity includes ceremony, category, film, nominee IDs (or name fallback), nominees, and `Detail` so separate source nominations remain distinct.

[`OscarEnrichmentService`](../../server/src/MediaDock.Application/OscarAwards/OscarEnrichmentService.cs) selects the newest eligible candidates through `IOscarEnrichmentRepository`, resolves each with the shared metadata resolver, and saves each completed result before proceeding. It compares the OMDb IMDb ID with both `OscarFilm.ImdbId` and the linked `Title.ImdbId`; a conflict is a retryable `imdb_id_mismatch` and does not apply metadata. [`PostgresOscarEnrichmentRepository`](../../server/src/MediaDock.Infrastructure/OscarAwards/PostgresOscarEnrichmentRepository.cs) persists status, attempt timestamps/count, deferred retry time, and OMDb fields on the related `Title` in the same `SaveChanges` transaction. Provider quota exhaustion defers the current film until the next UTC day and stops the batch; a locally denied reservation leaves the unprocessed candidate eligible. Other temporary errors use capped exponential retry delay. Oscar metadata updates do not modify `Title.FirstSeenAt`/`LastSeenAt` or create occurrences. The API dispatcher applies the configured candidate and Oscar request caps in addition to the shared RSS/Oscar daily HTTP budget.

The enrichment service writes its operation lifecycle through [`PostgresOscarEnrichmentRunRepository`](../../server/src/MediaDock.Infrastructure/OscarAwards/PostgresOscarEnrichmentRunRepository.cs). It inserts a `running` record before candidate selection, checkpoints counts and actual resolver HTTP attempts during processing, then records final status and completion time. `quota_stopped` distinguishes local/provider cap stops; `error_code` stores an exception type or safe provider code, not exception text or request URLs. An abrupt process termination can leave a `running` row with the last committed checkpoint.

[`PostgresOmdbRequestBudget`](../../server/src/MediaDock.Infrastructure/Metadata/PostgresOmdbRequestBudget.cs) uses one atomic PostgreSQL upsert per HTTP attempt. `omdb_daily_usage` stores total and Oscar request reservations by UTC date; RSS usage is derivable as total minus Oscar, and provider credentials are not stored in this counter table. `DailyRequestLimitReached` records when the configured shared cap was met. A provider 429 or OMDb quota response records a safe error code and sets `ProviderQuotaExceeded`, preventing subsequent HTTP reservations for that UTC date across API restarts. Other provider failures update `LastErrorCode` with a bounded code, never provider text or request URLs. The API exposes the last 30 UTC days of aggregates to the provider settings screen. Each fallback and retry reserves separately; metadata-cache hits do not reserve. A reservation is intentionally conservative if the process exits after reservation but before sending the HTTP request.

The OMDb API key is stored as plain text in `settings`, accepted through the unauthenticated local provider-settings endpoint, and omitted from all API responses. SQL backups include the key and must be protected accordingly. The key is sent to the fixed OMDb HTTPS endpoint by the API-hosted job handler; never log full outbound URLs or request bodies.

[`SourceItemIdentity.From`](../../server/src/MediaDock.Application/Ingestion/RssIngestionContracts.cs) builds an occurrence key as `entry:<trimmed feed entry id>` when an entry ID is present; otherwise it uses `url:<trimmed torrent URL>`. It throws if neither value is present. The database enforces uniqueness of `(source_id, source_item_key)`. [`PostgresRssIngestionRepository`](../../server/src/MediaDock.Infrastructure/Ingestion/PostgresRssIngestionRepository.cs) looks up a title by normalized IMDb ID first, then by normalized title, year, and media type only when the IDs are compatible. On the first real RSS observation it sets both title seen dates; later observations preserve the first and update the last. A title created by Oscar import is reused when its IMDb ID matches, without creating a duplicate title. A retry is limited to a violation of `ux_titles_imdb_id`, after clearing the EF tracker and rereading the canonical title; unrelated unique errors are not masked. Integration tests cover replay, Oscar-only-to-RSS promotion, conflict rejection, and simultaneous creation ([IngestionTests.cs](../../server/tests/MediaDock.IntegrationTests/IngestionTests.cs)).

`PostgresRssIngestionRepository.UpsertCatalogItemAsync` calls `BeginTransactionAsync`, saves and commits the title/occurrence upsert together, and rolls back on failure. A full scan is not one transaction: run creation, parse-log saves, each item upsert, and final run-summary save are separate repository operations. The metadata cache key is a lowercase SHA-256 digest of versioned normalized title, year, source type, and year semantics; the resolver caches confirmed `found` results for 30 days and `confirmed_not_found` results for 2 days, not transient failures ([MetadataResolver.cs](../../server/src/MediaDock.Application/Metadata/MetadataResolver.cs), [PostgresMetadataCacheStore.cs](../../server/src/MediaDock.Infrastructure/Metadata/PostgresMetadataCacheStore.cs)). Cache writes use a read-then-write by key followed by `SaveChanges`; the unique key is enforced by PostgreSQL, but the code does not provide a separate concurrent-upsert retry policy.

The API dispatcher acquires the PostgreSQL session advisory lock with `pg_try_advisory_lock` and releases it with `pg_advisory_unlock` for the duration of a claimed RSS scan, Oscar enrichment job, or dataset import. A competing dispatcher leaves queued work untouched for a later poll. This is not a general lock for API writes. [AdvisoryLockTests.cs](../../server/tests/MediaDock.IntegrationTests/AdvisoryLockTests.cs) verifies that a second lock acquisition fails until the first lease is released. The implementation is in [PostgresAdvisoryScanLock.cs](../../server/src/MediaDock.Infrastructure/Ingestion/PostgresAdvisoryScanLock.cs); [BackgroundJobDispatcher](../../server/src/MediaDock.Api/BackgroundJobs/BackgroundJobDispatcher.cs) holds the lease across claim and handler completion.
